01 / 목적무엇을 평가하나요

SoC는 여러 하드웨어 기능을 하나의 칩에 담은 시스템입니다. 그 안의 FIFO, 카운터, 중재기 같은 설계 블록을 HW IP라고 부릅니다. RTL은 이런 블록이 입력을 받아 어떤 출력을 내고 클록마다 상태를 어떻게 바꿀지 기술한 코드입니다.

사람이 IP를 설계할 때는 명세를 읽고 RTL을 작성한 뒤 검증합니다. 이 벤치마크는 그 과정의 일부를 에이전트에 맡깁니다. 평가자는 같은 명세와 시작 코드를 제공하고 에이전트가 제출한 RTL을 공통 채점기로 검사합니다.

FIFO를 예로 들어 보겠습니다. 명세에 “먼저 들어온 데이터를 먼저 내보내고, 가득 차면 입력을 받지 않으며, reset 때 저장 상태를 비운다”고 적혀 있습니다. 제출 RTL이 평소에는 잘 동작해도, 가득 찬 상태에서 데이터를 덮어쓴다면 이 과제는 실패입니다.

평가에서 자주 쓰는 말
용어뜻이번 평가에서 확인할 것
명세 · spec회로가 지켜야 할 동작과 인터페이스를 적은 문서포트, reset, 우선순위, 경계 동작이 충분히 설명되어 있는가
모델 · model명세와 코드 문맥을 읽고 답을 생성하는 언어 모델모델 이름, revision, 양자화, 생성 설정
에이전트 · agent모델을 사용해 파일을 읽고 코드를 고치거나 도구를 실행하는 프로그램사용 모델, 허용 도구, 수정·재시도 방식, 시간 예산
하네스 · harness평가 대상을 실행하고 입력·출력을 연결하는 실행 체계하네스·wrapper 버전과 실제 실행 설정
검사기 · checker제출 RTL에 입력을 주고 결과를 확인하는 테스트벤치공개 명세와 일치하는가, 알려진 오류를 찾아내는가
과제 묶음 · suite과제 목록과 허용 파일, 검사 조건을 고정한 평가 단위같은 suite와 같은 과제 부분집합으로 비교했는가

모델과 에이전트는 구분해서 평가합니다

같은 모델이라도 에이전트가 컴파일 오류를 읽고 수정할 수 있으면 결과가 달라질 수 있습니다. 반대로 같은 에이전트를 써도 모델을 바꾸면 명세 해석이나 코드 작성 결과가 달라질 수 있습니다. 그래서 평가 대상은 모델 + 에이전트·하네스 + 실행 설정의 조합으로 기록합니다.

  1. 1. 문제 제공명세, 시작 RTL, 허용 파일 목록
  2. 2. 생성·수정정해진 도구와 예산으로 RTL 제출
  3. 3. 독립 채점제출 사본을 별도 공간에서 검사
  4. 4. 증거 보존판정, 시간, 로그, 설정, 해시

최종 RTL의 기능 결과를 평가하므로 내부 추론의 품질이나 사람이 절약한 설계 시간을 직접 측정하지는 않습니다. 실제 개발 생산성을 판단하려면 통합·리뷰·추가 검증에 든 시간도 따로 조사해야 합니다.

02 / 범위현재 어떤 문제를 풀게 하나요

기본 suite는 작은 RTL 6과제로 구성되어 있습니다. CVDP에서 가져와 변형한 LFSR 1과제는 별도 suite입니다. 기본 실행은 7과제 전체를 포함하지 않습니다.

기본 suite: rtl-core-v1
과제분류주로 확인하는 동작
saturating_add생성 · generation8비트 덧셈, 최댓값 포화, overflow. 65,536개 입력 조합 검사 포함
priority_encoder생성 · generation여러 요청 중 낮은 번호 우선 선택, 요청 없음 처리, 모든 요청 mask
counter수정 · repair증가·유지, 최댓값 이후 wrap, reset 우선순위
fifo수정 · repair데이터 순서, full/empty, 동시 입출력, 데이터가 있는 상태의 reset
stream_pipeline다중 파일 수정 · repository받는 쪽이 멈췄을 때 데이터 유지, 전달·교체, reset
round_robin다중 파일 수정 · repository요청 선택, 수락 시 우선순위 갱신, 공정한 순환 처리

repository는 현재 작은 다중 파일 과제를 뜻합니다. 대규모 사내 IP 저장소를 탐색하고 수정하는 능력을 대표하지 않습니다. 생성 과제에도 시작 파일이 주어지므로 완전한 백지 설계와 구분해서 읽어야 합니다.

현재 확인하는 것

명세에 따른 기능, 경계 조건, 상태 변화, 제출 형식, 제한시간 내 완료 여부입니다. 일부 조합 회로는 모든 입력을 검사하고 순차 회로는 경계 입력과 seed를 사용한 시뮬레이션으로 검사합니다.

별도 검증이 필요한 것

합성 가능성의 엄밀한 확인, PPA, lint, formal, UVM, CDC/RDC, 모든 parameter 조합, 실리콘 signoff입니다. 코드·기능 coverage 수치도 현재 측정하지 않습니다.

정답 RTL로 먼저 채점기를 확인합니다

reference는 알려진 정답 구현이고 mutant는 일부러 오류를 넣은 구현입니다. 정답이 통과하고 오류 구현이 의도한 검사에서 실패해야 채점기를 사용할 근거가 생깁니다. 오류 구현의 컴파일이 깨졌다는 이유만으로 기능 오류를 찾아냈다고 판단하지 않습니다.

정답 구현 100%와 오류 구현 0%는 채점기 검증 결과입니다. 특정 모델이 100%를 달성했다는 뜻이 아닙니다. 보고서의 kind가 fixture_로 시작하는지 먼저 확인하세요.

CVDP LFSR 변형 결과는 공식 CVDP 점수와 구분합니다. HWE는 외부 공식 보고서를 가져오는 기능만 제공하며 이 저장소에서 공식 evaluator를 실행하거나 원본 실행을 인증한 결과가 아닙니다.

03 / 판정한 번의 성공은 무엇을 뜻하나요

단위뜻예시
과제 · task명세와 제출 파일이 정해진 하나의 문제FIFO 과제 1개
반복 · repeat같은 과제를 다시 생성·수정하는 실행FIFO를 3번 풀면 제출 기회 3회
검사 · check특정 동작을 확인하는 테스트벤치경계, reset, seed 입력 검사
검증 seed시뮬레이션의 입력 수열을 정하는 값--seeds 1,7,42
생성 seed모델 API에 전달하는 생성 설정HTTP config의 seed. 검증 seed와 별개
6과제 × 3반복 = 계획한 과제 실행 18회각 실행에 3개 check × 3개 검증 seed = 필수 검사 9개

모든 제출이 채점까지 진행되면 총 162개의 check·seed 판정이 생깁니다. 하지만 문제 종류는 6개이고 성공률의 분모는 18회입니다. 162개의 독립 문제를 풀었다고 계산하면 안 됩니다. 컴파일 실패 때는 해당 seed 판정이 실패로 기록되고 시뮬레이션은 실행되지 않을 수 있습니다.

필수 검사 9개 중 8개가 통과해도 과제는 실패입니다

경계 · seed 1 ✓경계 · seed 7 ✓경계 · seed 42 ✓reset · seed 1 ✓reset · seed 7 ✓reset · seed 42 ✓랜덤 · seed 1 ✓랜덤 · seed 7 ✓랜덤 · seed 42 ✕

이 실행의 과제 상태는 FAIL입니다. 검사 통과 비율 8/9는 어떤 부분이 고장 났는지 살펴보는 보조 정보입니다. 기능 점수에 8/9점의 부분 점수를 주지는 않습니다.

이 저장소가 직접 실행하는 채점(native 채점)의 PASS에는 모든 필수 검사의 컴파일 성공, 시뮬레이터 정상 종료, 시간·출력 제한 준수, 정확히 한 번의 신뢰된 완료 표식이 필요합니다. 단순히 로그에 PASS라는 문자열이 있거나 에이전트 프로세스가 정상 종료했다는 이유로 성공 처리하지 않습니다.

agent.status = ok는 제출 처리 또는 에이전트 실행이 끝났다는 상태입니다. RTL이 정답인지는 뒤이은 채점에서 결정합니다. --repeats는 생성 seed를 자동으로 바꾸지 않으며 같은 설정의 반복이 독립적인 생성 표본을 보장하지도 않습니다.

simulation_seconds		개별 컴파일 및 시뮬레이션 프로세스의 경과 시간느린 단계 진단. compile 기록은 seed별 행에서 중복될 수 있음
별도 실측처음부터 끝까지 걸린 시간준비·export·생성·채점·보고서 작성까지 포함한 전체 경과 시간실행 시작·종료를 별도 측정. 위 필드의 합과 정확히 같지 않음

컴파일 시간을 중복해서 더하지 마세요. Checker 하나는 한 번 컴파일한 뒤 여러 seed로 실행합니다. checks.csv에는 같은 컴파일 시간이 각 seed 행에 반복됩니다. 합산할 때는 (task_id, repeat, check)마다 한 번만 셉니다. 채점 seconds에 compile·simulation 시간을 다시 더하는 것도 중복입니다.

--agent-timeout은 과제 생성 1회에 적용합니다. --check-timeout은 개별 컴파일과 개별 seed 시뮬레이션에 각각 적용합니다. 예를 들어 check-timeout 10초를 지정해도 한 과제의 총 채점 시간에는 10초 제한이 적용되지 않습니다.

Token 사용량과 비용

usage는 HTTP 서버가 돌려준 사용량을 그대로 저장한 값입니다. 서버가 제공하면 입력·출력 token 등을 확인할 수 있지만 필드와 계산 범위는 서비스마다 다를 수 있습니다. Command adapter는 이 값을 자동으로 수집하지 않습니다. 빈 {}는 미측정이며 0 token이나 무료라는 뜻이 아닙니다.

Token 수가 적다는 이유만으로 더 저렴하다고 판단할 수는 없습니다. 모델마다 tokenizer가 다를 수 있고 사내 서버의 GPU·운영 비용도 별도입니다. 비용을 비교하려면 같은 비용 산정 범위를 정하고 실패한 실행의 비용까지 포함하세요.

별도 분석: 검사 통과율, 컴파일 성공률, 시간의 중앙값·상위 지연, 성공 1건당 비용, 신뢰구간, pass@k는 현재 기본 보고서가 자동 계산하지 않습니다. 필요하면 원자료로 계산하되 대상 실행, 분모, 미측정 처리 방법을 함께 적으세요.

05 / 계산 예시같은 결과도 분모를 바꾸면 다르게 보입니다

6과제를 3회씩 실행한다고 가정해 보겠습니다. 18회 중 성공 12회, 기능 실패 3회, 인프라 오류 2회, 미기록 1회라면 대표 성공률은 12/18 = 66.7%입니다. 인프라 오류와 미기록이 있으므로 평가 미완료로 읽습니다.

인프라 오류와 미기록을 빼면 12/15 = 80%가 되지만 이는 다른 분모로 계산한 값입니다. 이를 원래 성공률 대신 제시하면 실행 환경의 문제를 가리게 됩니다.

성공률 계산기 설명용 · 실제 결과 불러오기 아님

숫자를 바꾸면 계획 수와 결과 합계를 검사합니다. 합계가 맞지 않으면 점수를 계산하지 않습니다.

인프라 외 실패에는 이 계산기의 편의상 fail, timeout, agent_error, invalid_submission 등을 합쳐 넣습니다.

66.7%

성공 12 / 계획 18 · 기록 17 · 인프라 오류 2 · 미기록 1

평가 미완료. 인프라 오류와 미기록을 확인하세요.

성공인프라 외 실패인프라 오류미기록

기본 suite에서 1회씩만 실행하면 한 과제의 성공 여부에 따라 전체 성공률이 약 16.7%p 움직입니다. 3회 반복에서는 실행 1건이 약 5.6%p에 해당합니다. 반복을 늘려도 문제 종류는 그대로 6개이므로 다양한 IP를 평가한 것과 같지는 않습니다.

06 / 해석성공률·시간·사용량을 어떻게 함께 비교하나요

지표마다 답하는 질문이 다릅니다. 성공률은 요구 기능을 완성한 빈도, 시간은 작업을 마칠 때까지의 대기, usage는 서비스가 기록한 자원 사용량입니다. 단위가 다른 값을 임의로 더해 하나의 점수로 만들기보다 아래 순서로 읽는 편이 판단 근거를 남기기 쉽습니다.

  1. 비교 조건을 확인합니다. 같은 suite·protocol·결과 종류인지 보고 반복 수와 wrapper 정책도 대조합니다.
  2. 평가가 완료되었는지 확인합니다. 인프라 오류와 미기록이 남았으면 능력 비교 결론을 유보합니다.
  3. 기능 성공률과 실패 과제를 봅니다. 전체 비율이 같아도 실패한 IP 기능은 다를 수 있습니다.
  4. 같은 과제에서 시간을 비교합니다. 성공·실패를 구분하고 시간 초과 실행도 함께 표시합니다.
  5. 측정 가능한 자원을 비교합니다. Usage와 비용의 수집 범위가 같은지 확인한 뒤 판단합니다.
가상 예시: 동일한 6과제 × 3회, 인프라 오류·미기록 없음
구성성공 / 계획성공률생성 시간 중앙값* (A·B·C가 모두 성공한 동일 실행 쌍 기준)해석
A15/1883.3%60초B보다 성공 횟수가 많음
B12/1866.7%30초공통 성공 집합에서 빠르지만 전체 성공률은 낮음
C15/1883.3%45초A와 성공 횟수가 같고 공통 성공 집합에서는 더 빠름

* task_id·repeat를 맞춘 공통 성공 집합을 별도로 분석한 가상 값입니다. 현재 보고서의 자동 집계 항목이 아닙니다. 실제 분석에서는 공통 집합 크기, 나머지 실행의 시간·실패도 함께 공개하세요.

A와 B의 성공률 차이는 16.7%p입니다. 상대 증가율로는 25%이지만 보고서에는 “15/18 대 12/18, 차이 3회”를 함께 적는 편이 오해를 줄입니다. C가 A보다 빨라도 실패한 과제, 사용량, 반복별 변동이 다르면 최종 선택이 달라질 수 있습니다.

평균 시간만 비교하면 생기는 문제

B가 어려운 과제에서 2초 만에 오류로 종료했다면 전체 평균 시간이 낮아질 수 있습니다. 이를 설계 속도가 빠르다고 해석하면 곤란합니다. 반대로 성공한 실행만 골라 비교하면 서로 다른 난도의 과제를 비교할 수 있습니다.

전체 실행의 상태별 시간과 공통 성공 과제의 시간을 함께 제시하세요. 중앙값을 사용했다면 표본 수와 범위도 적습니다. 생성이 300초 제한에 걸렸다는 기록은 그 시간 안에 끝내지 못했다는 뜻입니다. 실제 완료 시간이 300초라는 의미는 아닙니다.

성공률이 같아도 같은 능력은 아닙니다

A는 조합 회로에서 강하고 B는 FIFO·파이프라인에서 강할 수 있습니다. 전체 성공률 다음에는 업무별 결과와 과제별 성공·실패 표를 보세요. 회사에서 필요한 기능을 기준으로 별도 가중 점수를 만들려면 가중치와 대상을 실행 전에 정하고 기본 성공률도 함께 공개합니다. 현재 도구는 그런 가중 점수를 계산하지 않습니다.

숫자가 작게 차이 나면 관찰한 차이로 보고하세요. 한 번의 순위만으로 우열을 확정하지 않습니다. 같은 과제의 반복 결과를 확인하고 문제 범위를 넓혀 재평가하세요. 이 도구는 통계적 유의성 검정이나 신뢰구간을 제공하지 않으며 검증 seed 수를 독립 표본 수로 사용할 수도 없습니다.

07 / 실험 설계바꾸려는 요소 하나를 먼저 정하세요

알고 싶은 차이바꿀 것고정할 것결과를 부르는 방법
모델 차이모델 이름·revision 등 평가 대상에이전트·하네스, 허용 도구, 명세, 생성 설정과 예산, 채점 조건동일 하네스를 사용한 모델 비교
에이전트 차이에이전트·하네스모델·revision·양자화, 문제·채점 조건, 비교하려는 도구 접근·예산 조건동일 모델을 사용한 에이전트 비교
실무에 쓸 구성 차이모델과 에이전트 또는 예산을 함께 변경문제와 채점 기준, 운영 요구사항구성 조합 비교. 원인을 모델 하나로 돌리지 않음

에이전트의 도구 사용 방식 자체를 비교하려면 허용할 도구 범위와 예산을 먼저 정하세요. 한쪽에만 추가 도구나 긴 시간을 주었다면 그 조건까지 포함한 조합 비교로 보고합니다.

기본 run은 순차 실행합니다. A를 먼저, B를 나중에 실행하면 서버 부하가 달라질 수 있으므로 상태를 기록하세요. 반복 실험에서는 순서를 바꾸거나 교대로 실행하는 방법도 검토할 수 있지만 현재 CLI가 실험 순서를 자동 설계하지는 않습니다.

해시가 같으면 모든 조건이 같을까요

suite_fingerprint는 manifest, 명세, 시작 RTL, checker 등의 내용으로 계산한 식별값입니다. 과제 부분집합 선택도 반영합니다. protocol_fingerprint에는 이 값과 검증 seed, 제한시간, runner 정보, simulator 정보, sandbox 등이 들어갑니다.

현재 native protocol의 포함 범위
자동 비교 조건에 포함별도로 확인할 조건
Suite hash, 검증 seed 목록, check timeout, runner 버전·Python 소스 hash, iverilog 정보(경로 포함), 실제 sandbox 사용 여부반복 횟수, vvp 버전, host/GPU 상태, 서버 부하
run에서는 adapter 유형, agent timeout, temperature·max_tokens·생성 seed도 추가모델·하네스 식별 정보, endpoint, wrapper 내부 설정·재시도, 실제 도구 권한

compare는 같은 protocol_fingerprint와 kind끼리 표를 만듭니다. 모델 이름이 비교 조건에서 빠지는 것은 서로 다른 모델을 비교하기 위해서입니다. 다만 같은 표에 묶였다는 사실만으로 반복 수나 wrapper 정책까지 같다고 보장하지는 않습니다. adapter_config_sha256는 별도 기록이며 그룹을 나누는 키가 아닙니다.

OpenAI-compatible 단발 호출과 command agent는 서로 다른 protocol입니다. 반입 RTL을 채점하는 grade도 생성까지 실행한 run과 결과 종류가 다릅니다. 다른 그룹의 해시를 수동으로 같게 바꿔 순위를 만들지 마세요.

Command 설정에 temperature, max_tokens, seed를 적어도 wrapper에 자동 적용되지는 않습니다. Runner는 지정한 argv를 실행합니다. 실제 wrapper 설정과 기록이 일치하는지 확인해야 합니다.

09 / 실행첫 평가를 진행하는 순서

모든 명령은 저장소 루트에서 실행합니다. Linux, Python 3.10 이상, iverilog, vvp가 필요합니다. 격리가 필요한 채점에는 사용할 수 있는 bubblewrap 환경도 준비하세요. 아래 출력 경로가 이미 있다면 새 이름으로 바꿉니다.

1. 채점 환경부터 확인합니다

python3 -m hwbench doctor
python3 -m hwbench list
python3 scripts/validate.py

doctor는 도구 버전과 격리 가능 여부를 출력합니다. validate.py는 회귀 테스트, 정답·오류 구현, CVDP 변형을 검사하고 가능하면 전체 프로세스의 인터넷 차단 시험도 실행합니다. 출력된 artifacts/validation-<UTC시간>/index.html을 여세요. 인터넷 차단 시험이 SKIPPED라면 그 항목을 검증했다고 보고하지 않습니다.

2. 모델과 하네스 설정을 준비합니다

단발 모델은 configs/openai-compatible.example.json, 도구를 사용하는 에이전트는 configs/command.example.json을 복사해 사용합니다. 이름만 바꾸지 말고 실제 revision·양자화·하네스 버전도 기록하세요. 키는 평문 대신 환경변수 이름인 api_key_env로 지정합니다.

cp configs/openai-compatible.example.json configs/model-a.json
# model-a.json의 base_url, model, model_revision, quantization 등 실제 값 입력
# 같은 조건으로 비교할 model-b.json도 준비

HTTP adapter는 Chat Completions 단발 응답에서 허용 파일 전체를 담은 JSON을 받습니다. Command adapter는 wrapper에 workspace와 prompt 경로를 넘기고 wrapper가 허용 RTL을 수정한 뒤 종료하도록 연결합니다. 실제 사내 endpoint와 인증은 해당 환경에서 확인해야 합니다.

3. 같은 조건으로 실행합니다

python3 -m hwbench run --config configs/model-a.json \
  --repeats 3 --seeds 1,7,42 \
  --agent-timeout 300 --check-timeout 10 \
  --sandbox required --out artifacts/model-a-r1

python3 -m hwbench run --config configs/model-b.json \
  --repeats 3 --seeds 1,7,42 \
  --agent-timeout 300 --check-timeout 10 \
  --sandbox required --out artifacts/model-b-r1

위 명령은 두 설정 파일이 같은 실행 방식과 비교 조건으로 준비되었다는 가정입니다. --sandbox required가 실패하면 격리 환경을 먼저 확인하세요. 모델을 여러 번 실행하면 시간과 자원을 사용하므로 반복 수와 예산을 실험 기록에 남깁니다.

Command agent를 실제 blind 평가에 사용한다면 이 실행 명령만으로는 격리가 충분하지 않습니다. Agent가 채점 저장소를 볼 수 없는 별도 환경을 준비하거나 다음 장의 export·grade 방식을 사용하세요.

4. 보고서를 비교하고 원자료를 보존합니다

python3 -m hwbench compare \
  artifacts/model-a-r1 artifacts/model-b-r1 \
  --out artifacts/model-comparison-r1

# 기존 결과에서 상세 보고서 다시 만들기
python3 -m hwbench report artifacts/model-a-r1

비교 파일은 artifacts/model-comparison-r1/comparison.html입니다. 예상과 달리 그룹이 나뉘면 protocol을 대조하세요. 재시도 결과는 새 디렉터리에 보존하고 원래 실패 기록을 지우지 않습니다.

선택 실행에는 --tasks counter,fifo를 사용할 수 있습니다. 부분집합이 달라지면 평가 조건도 달라집니다. CVDP 변형은 --suite benchmarks/cvdp_adapted/suite.json으로 별도 선택합니다.

10 / 폐쇄망문제 실행 환경과 채점 환경을 분리합니다

에이전트가 정답 RTL이나 hidden checker를 읽으면 명세를 구현하는 능력과 답을 찾아오는 능력이 섞입니다. 실제 blind 평가에서는 명세·시작 RTL·허용 파일 목록만 전달하고 채점 자료는 접근할 수 없는 환경에 둡니다.

  1. 채점 측: export문제만 내보내기
  2. Agent 측: 실행허용 파일을 수정하고 실행 조건 기록
  3. Agent 측: 제출과제별 RTL과 실행 기록 반환
  4. 채점 측: grade고정된 검사로 평가하고 증거 보존
# 채점 저장소에서 문제만 내보내기
python3 -m hwbench export --out artifacts/prompts-r1

# 별도 환경의 실행 결과를 반입한 뒤 채점
python3 -m hwbench grade \
  --submissions /path/to/returned-submissions \
  --label 'model-A + harness-B / r1' \
  --seeds 1,7,42 --check-timeout 10 --sandbox required \
  --out artifacts/imported-r1

반환 디렉터리는 <task_id>/rtl/... 구조를 유지합니다. JSONL로 반환할 때는 각 줄을 {"id":"task_id","files":{"rtl/file.sv":"전체 RTL 문자열"}} 형식으로 작성하고 import-files로 변환합니다.

python3 -m hwbench import-files \
  --responses /path/to/responses.jsonl --out artifacts/submissions-r1

grade는 받은 RTL만 평가하므로 생성 시간·usage·모델 설정을 자동 복원하지 못합니다. CLI의 label만으로 조건을 충분히 설명할 수 없습니다. 생성 서버의 실행 기록, wrapper 버전, 예산, 오류와 재시도 내역을 별도 실험 기록으로 함께 반입하세요. 반복 평가에서는 각 반복의 제출과 채점 결과를 따로 보존합니다.

RTL compile/simulation에 적용하는 bubblewrap은 에이전트 격리를 대신하지 않습니다. 에이전트의 파일·도구 접근은 별도 머신, 사용자 권한 또는 컨테이너 구성으로 제한해야 합니다. 사내 명세와 RTL을 외부 API로 보내지 말고 허용된 endpoint만 사용하세요.

오프라인 패키지 전달

python3 -m hwbench bundle --out artifacts/hwbench-offline.tar.gz
python3 -m hwbench verify-bundle artifacts/hwbench-offline.tar.gz

Bundle에는 소스와 과제·문서·설정이 들어가지만 Python·EDA 바이너리나 실행 결과는 들어가지 않습니다. 필요한 OS 패키지는 별도로 준비하고 configs/에 민감한 설정이 들어 있는지 확인하세요. 검증 결과는 실행 디렉터리 전체를 별도로 전달합니다.

11 / 진단점수가 낮을 때 어디부터 확인하나요

관찰한 현상먼저 확인할 내용피해야 할 해석
컴파일 전에 제출 거부파일 누락, 허용 경로, JSON 형식, 금지된 RTL 구문회로 알고리즘을 이해하지 못했다고 바로 결론 내림
컴파일 실패문법, 포트·모듈 연결, 언어 지원, compile 로그도구가 존재하는데도 모든 컴파일 오류를 인프라 문제로 분류
특정 reset·경계 검사 실패명세의 reset 우선순위, 동시 입출력, hold, wrap 규칙대부분의 check가 통과했으므로 과제도 성공이라고 계산
Agent는 ok인데 과제 실패독립 채점의 reason과 check 로그정상 종료를 기능 PASS로 취급
Timeout이 많음생성/컴파일/시뮬레이션 중 어느 단계인지, 예산과 서버 부하모든 시간 초과를 하나의 원인으로 묶음
정답·mutant 검증부터 실패채점 환경과 checker·명세 변경 내역채점기가 검증되지 않은 상태에서 모델 순위를 발표
반복마다 결과가 크게 다름과제별 변동, 생성 설정, 서버 상태, wrapper 재시도가장 좋은 반복만 남겨 대표 점수로 사용
100%인데 실무 IP에서 실패벤치마크와 실제 IP의 범위 차이, parameter·통합·검증 요구작은 suite 성공을 전체 SoC 설계 능력으로 일반화

명세가 모호하거나 checker가 명세와 다른 동작을 요구한다면 먼저 과제를 수정해야 합니다. 수정한 조건은 새로운 평가 버전으로 취급하고 비교 대상 모두를 다시 실행하세요. 특정 모델의 제출만 통과하도록 checker를 바꾸지 않습니다.

12 / 판단결과를 이렇게 정리하세요

보고에는 관찰한 결과, 비교 조건, 해석 범위를 함께 적습니다. 아래 문장은 모두 평가가 끝난 가상 예시입니다.

동일한 rtl-core-v1 6과제를 각 3회 실행했다. 인프라 오류와 미기록은 없었다. A는 15/18회(83.3%), B는 12/18회(66.7%) 성공했다. 같은 하네스와 생성·채점 예산을 적용했으며, A가 이 조건에서 3회 더 성공했다. 공통 성공 집합에서는 B의 생성 시간 중앙값이 낮았다. 순차 회로의 과제별 실패를 추가로 분석한 뒤 사내 IP 과제로 재평가한다.

인프라 오류가 남았다면 다음처럼 씁니다.

A는 계획 18회 중 12회 성공했다(66.7%). 인프라 오류 2회와 미기록 1회가 있어 평가 미완료 상태다. 환경 복구 후 새 실행을 수행하며 원래 결과도 보존한다. 현재 결과만으로 모델 간 우열을 확정하지 않는다.

결과 공유 전 점검표

  • 어떤 모델·revision·하네스·wrapper를 평가했는지 식별할 수 있나요?
  • Suite, 과제 목록, seed, 예산, 도구, sandbox, 반복 수가 비교 목적에 맞게 통제되었나요?
  • Fixture 검증과 실제 model_run, 반입 submission, upstream_import를 구분했나요?
  • 성공/계획 수, 인프라 오류, 미기록을 비율과 함께 표시했나요?
  • 업무별 분모와 전체 분모의 차이, 시간의 측정 범위를 설명했나요?
  • 실패한 실행과 timeout, 미측정 usage를 빼거나 0으로 바꾸지 않았나요?
  • 실제로 채점한 RTL, 로그, config 식별값, hash를 다시 확인할 수 있나요?
  • 이번 결과로 판단할 수 있는 IP 범위와 추가 검증이 필요한 부분을 적었나요?

합성·PPA를 추가한다면 기능 검증을 통과한 RTL을 대상으로 동일한 tool, library, clock·timing constraint를 적용하세요. 전력·성능·면적은 기능 성공률과 별도 축으로 보고해야 합니다. 현재 HWBench 기능 점수만으로 이 값을 추정할 수는 없습니다.

자주 묻는 질문

성공률 100%면 RTL 검증이 끝난 건가요?

고정된 명세와 필수 시뮬레이션 검사를 모두 통과한 결과입니다. 유한한 검사가 모든 상황의 정확성이나 제품 signoff를 보장하지는 않습니다. 실제 IP에 필요한 검증을 별도로 수행해야 합니다.

검증 seed를 늘리면 모델 평가 표본 수도 늘어나나요?

Seed를 사용하는 검사에서는 같은 제출 RTL을 더 많은 입력 수열로 검사합니다. Seed를 사용하지 않는 boundary·exhaustive 검사는 같은 입력을 반복할 수 있으므로 seed 추가가 항상 새로운 경우의 수나 coverage 증가를 뜻하지는 않습니다. 생성한 제출물 수나 문제 종류는 늘어나지 않습니다. 검사를 엄격하게 바꾸었으므로 기존 seed 조건의 점수와 직접 비교하지 않습니다.

3번 중 한 번 성공하면 pass@3인가요?

현재 기본 성공률은 모든 계획 실행의 성공 비율입니다. 한 과제를 3회 실행해 한 번 성공했다면 그 과제의 반복 성공률은 1/3입니다. 여러 후보 중 하나라도 성공한 과제의 비율을 따로 분석하려면 생성·선택 정책과 분모를 정의해야 합니다. 도구가 이를 pass@k로 자동 계산하지는 않습니다.

인프라 오류를 제외한 점수를 보고해도 되나요?

보조 분석으로 별도 분모를 명시할 수는 있지만 기본 점수를 대신하면 안 됩니다. 계획 수 기준 성공률과 장애 수, 평가 미완료 상태를 함께 공개하고 장애 복구 후 다시 실행하세요.

모델 A는 단발 호출, 모델 B는 도구 사용 agent로 비교해도 되나요?

실무 구성의 차이를 관찰할 수는 있지만 모델만의 능력 차이로 해석할 수는 없습니다. 실행 protocol도 다르므로 자동 비교에서는 별도 그룹으로 표시합니다.

실패할 때마다 다시 시도해서 가장 좋은 결과를 써도 되나요?

현재 runner는 자동 best-of 선택을 하지 않습니다. 수동 재실행을 포함한 모든 시도와 예산을 기록하세요. 재시도 가능한 운영 정책을 평가하려면 그 정책을 사전에 정해 모든 대상에 동일하게 적용하고 첫 실행의 성공률과 구분해야 합니다.

사용량이 비어 있거나 시간이 0이면 비용이 없었던 건가요?

생성 오류가 난 경로는 채점 시간이 0일 수 있고 command 실행의 usage는 자동 수집되지 않습니다. 값의 존재 여부와 해당 단계 실행 여부부터 확인하세요. 미측정이나 미실행을 무료로 해석하지 않습니다.

구현 근거와 용어 찾아보기

이 가이드는 아래 저장소 파일의 현재 동작을 설명합니다. 파일 경로는 개발자가 확인할 위치이며 문서를 읽을 때 해당 파일이나 인터넷 연결이 필요하지는 않습니다. 구현이 바뀌면 지표 정의와 명령 예시도 함께 검토해야 합니다.

설명한 내용구현 근거
집계 분모, 보고서, 비교 그룹hwbench/reporting.py의 summary, write_report, compare_reports
PASS, RTL 정책, 채점 시간, protocolhwbench/grader.py의 grade_task, new_result, grade
Adapter, 반복, 생성 시간·usagehwbench/execution.py의 run, openai_completion, _http_request

명령, 부분집합, fixture 검증, bundlehwbench/cli.py, scripts/validate.py
현재 과제와 검사 구성benchmarks/core/suite.json, benchmarks/cvdp_adapted/suite.json
HWE 결과 매핑과 가져오기 한계hwbench/upstream.py
Protocol
문제와 실행·채점 조건을 묶어 정한 평가 규약입니다. 같은 protocol로 평가했는지 확인한 뒤 결과를 비교합니다.
Token / tokenizer
Token은 모델이 텍스트를 처리할 때 나누는 단위이고, tokenizer는 텍스트를 그 단위로 나누는 도구입니다. 같은 문장도 tokenizer에 따라 token 수가 달라질 수 있습니다.
Temperature / max_tokens
각각 모델 생성의 무작위성을 조절하는 설정과 최대 출력 token 예산입니다. 같은 값을 사용해도 서버가 지원하고 적용하는 방식은 확인해야 합니다.
Revision
같은 모델 이름 안에서도 실제 평가한 가중치나 구현 버전을 구분하는 값입니다.
양자화
모델을 실행할 때 수치 표현 정밀도를 줄이는 방식입니다. 같은 모델 이름이라도 설정이 다르면 결과가 달라질 수 있어 기록합니다.
Fingerprint / hash
내용이나 설정을 해시 함수로 계산한 식별값입니다. 조건 변경을 찾는 데 사용하며 점수 자체가 아닙니다.
Backpressure
받는 쪽이 준비되지 않아 보내는 쪽의 전송을 멈추게 하는 흐름 제어입니다.
Formal / PPA / CDC·RDC
