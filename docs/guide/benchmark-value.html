1. 왜 필요한가

요즘 AI는 RTL 코드를 그럴듯하게 작성합니다. 문제는 그럴듯한 것과 맞는 것이 다르다는 점입니다. 소프트웨어는 실행해 보고 바로 고칠 수 있지만, 칩 설계의 오류는 검증 후반이나 그 이후에 발견될수록 수정 비용이 커집니다. 겉으로 멀쩡한 RTL이 reset 직후나 데이터가 밀리는 상황에서만 틀리면 데모로는 드러나지 않습니다.

사내에서는 선택지가 많습니다. 사내 서버에서 돌리는 여러 오픈 모델(온프레미스 LLM), Claude 같은 상용 모델, 그리고 Claude Code와 같은 CLI 코딩 도구가 있습니다. 이들을 다음 방식으로 고르면 판단이 흔들립니다.

데모로 고르기

잘 나온 예시 몇 개는 평균 실력을 말해 주지 않습니다.

공개 순위로 고르기

공개 벤치마크의 과제와 도구 환경은 사내 IP 개발 조건과 다릅니다.

사용 후기로 고르기

사람마다 시킨 일과 도구 설정이 달라 서로 비교할 수 없습니다.

HWBench는 이 판단을 같은 문제, 같은 채점, 남는 기록으로 바꾸기 위한 사내 평가 도구입니다. 외부 인터넷 없이 동작합니다.

2. 기본 아이디어: AI에게 입사 시험을 봅니다

채용 시험과 같습니다. 모든 지원자에게 같은 문제지를 주고, 답안은 정답을 아는 채점관이 같은 기준으로 봅니다. 지원자는 채점 기준을 볼 수 없습니다.

입사 시험HWBench
문제지설계 명세. 포트, clock, reset, 동작 조건을 글로 적은 문서
지원자평가 대상 AI 구성
답안지AI가 작성하거나 고친 RTL 파일
비공개 채점표AI에게 숨긴 검사 코드(testbench). 시뮬레이터로 실제 동작을 확인
성적표과제별 합격 여부, 실패 원인, 소요 시간과 전체 기록

핵심은 AI의 설명을 믿지 않는다는 점입니다. AI가 "완료했습니다"라고 말해도 점수가 되지 않습니다. 제출된 RTL이 시뮬레이션을 통과해야만 합격입니다.

3. 무엇을 비교하는가: 모델과 도구는 다릅니다

많은 사람이 "AI"라고 묶어 말하지만, 실제로는 두 부분으로 나뉩니다.

모델 (두뇌)

답을 생성하는 LLM입니다. 사내 서버의 오픈 모델이나 Claude 모델이 여기에 해당합니다.

실행 도구 (손발)

모델이 파일을 읽고 고치고 시뮬레이터를 돌리게 해 주는 프로그램입니다. Claude Code 같은 CLI가 여기에 해당합니다. harness라고도 부릅니다.

실행 구성 (팀)

모델과 도구의 조합, 그리고 허용 도구·시간 제한 같은 설정까지 합친 단위입니다. 실제로 시험 보는 단위입니다.

공정한 비교의 규칙: 한 번에 하나만 바꿉니다

두 조건을 동시에 바꾸면 무엇 때문에 좋아졌는지 알 수 없습니다.

알고 싶은 것고정할 것바꿀 것예시
어떤 사내 모델이 나은가실행 도구, 온도, 시간 제한모델모델 A와 B를 같은 도구로 비교
어떤 Claude 모델이 나은가Claude Code 버전, 허용 도구, 예산Claude 모델Opus와 Sonnet을 같은 Claude Code 설정으로 비교
어떤 CLI 도구가 나은가모델과 추론 설정실행 도구같은 모델을 쓸 수 있는 두 CLI를 비교
사내 조합과 상용 조합 중 무엇이 나은가문제, 채점, 시간 제한조합 전체"조합 간 차이"로만 말하고 원인을 단정하지 않음

주의할 해석: 사내 모델과 Claude Code 조합을 비교해 차이가 났다면, 모델이 좋아서인지 도구가 좋아서인지 알 수 없습니다. 이 경우 어느 쪽이 실무에 쓸 만한지는 판단할 수 있지만 원인은 말할 수 없습니다.

4. 어떤 문제를 푸는가

현재 저장소에는 인터넷 없이 돌릴 수 있는 RTL 과제 308개가 들어 있습니다. 문제 유형은 크게 두 가지입니다. 생성은 명세만 보고 처음부터 작성하고, 수정은 결함이 있는 RTL을 명세에 맞게 고칩니다.

묶음과제 수내용무엇을 보여 주는가
공개 소형 과제159VerilogEval, RTLLM을 변형한 조합·순차·FSM 회로기본기의 하한선
주입 결함 수정122공개 과제 정답에 결함을 넣어 고치게 함명세와 코드를 대조해 고치는 능력
SoC형 블록20APB, AXI-Lite, AXI-Stream, CDC FIFO, ECC, CRC, 타이머 등실제 IP에 가까운 인터페이스 설계
기존 소형 과제7카운터, FIFO, LFSR 등동작 확인용 기준 과제

문제 예시: skid buffer

"데이터를 두 개까지 저장하는 파이프라인 레지스터를 만드세요. 뒤쪽이 멈춰도 데이터를 잃으면 안 되고, 받을 수 있다는 신호는 뒤쪽 신호에 조합적으로 의존하면 안 됩니다." 이런 조건이 표로 정리된 명세가 주어집니다. 흔한 오답은 평소에는 동작하지만 뒤쪽이 멈추는 순간 데이터를 하나 잃는 코드입니다.

과제가 이렇게 많은 이유는 단순합니다. 다음 절에서 보듯 과제 수가 적으면 우연히 잘 본 것인지 실력인지 구분할 수 없습니다. 다만 공개 과제가 많아도 실제 사내 IP를 대표하지는 않으므로, 사내 RTL의 실제 버그 수정 이력으로 만든 과제를 추가하는 것이 다음 단계입니다.

5. 어떻게 채점하는가

합격 기준은 엄격합니다. 컴파일 성공, 시뮬레이션 정상 종료, 준비된 모든 검사를 입력 조합(seed)별로 전부 통과해야 합니다. 하나라도 어긋나면 그 과제는 불합격입니다. 빈 답안, 시간 초과, 문법 오류도 모두 불합격입니다. 반대로 서버 장애처럼 AI 잘못이 아닌 문제는 불합격과 구분해 "평가 미완료"로 표시합니다.

채점기 자신도 먼저 시험합니다

시험지가 잘못되면 성적도 의미가 없습니다. 그래서 모든 과제는 평가에 쓰기 전에 다음을 통과합니다.

정답은 합격하는가

기준 RTL이 모든 검사를 통과해야 합니다.

오답은 잡아내는가

일부러 결함을 넣은 RTL이 기능 오류로 탈락해야 합니다. 빈 코드와 입력을 무시하고 값을 고정한 RTL도 탈락해야 합니다.

다른 정답도 인정하는가

구조가 다른 올바른 구현이 통과하는지 일부 과제에서 확인했습니다.

기준을 통과하지 못한 공개 과제는 조용히 지우지 않고 제외 사유와 함께 기록했습니다.

6. 결과는 어떻게 읽는가

성공률 하나만 보면 놓치는 것이 많습니다. 보고서는 아래 순서로 읽습니다.

질문보는 지표쉽게 말하면
시험이 제대로 치러졌나인프라 오류, 미기록정전으로 시험이 중단된 답안은 없는가
얼마나 맞혔나등급별 성공률합격한 과제 수 / 계획한 과제 수
어디에 강하고 약한가영역·난이도별 결과연산은 잘하지만 인터페이스는 약한가
얼마나 믿을 수 있나95% 구간우연을 감안한 성적의 범위
왜 틀렸나실패 원인문법 오류인가, 동작이 틀렸는가, 시간이 부족했는가
매번 같은가반복 일관성같은 문제를 다시 풀어도 맞히는가
A가 B보다 나은가과제 단위 짝비교같은 문제끼리 비교해 어느 쪽이 더 자주 이겼는가
통과한 코드가 쓸 만한가품질 지표, PPA불필요한 latch는 없는가, 면적·속도·전력은 어떤가
비용은 얼마나 드나시간, 사용량측정된 값만 사용하고 측정하지 않은 값은 비워 둠

과제 수가 왜 중요한가

성공률이 같아도 시험 문제 수에 따라 믿을 수 있는 정도가 다릅니다. 아래 막대를 움직여 보세요. 진한 구간이 넓을수록 불확실합니다.

0%50%100%

95% 구간: 약 60%에서 86%

설명용 가상 수치입니다. 실제 측정 결과가 아닙니다.

구성 A가 40개 중 30개를 맞혀 75%이면 실제 실력의 범위는 대략 60%에서 86%입니다. 과제가 300개이고 225개를 맞혔다면 범위가 70%에서 80%로 좁아집니다. 40개 시험에서 75%와 70%가 나온 두 구성은 사실상 구분되지 않습니다.

대략적인 기준으로, 같은 과제로 짝지어 비교할 때 성공률 20%p 차이를 가리려면 약 60개, 10%p 차이를 가리려면 약 230개의 서로 다른 과제가 필요합니다. 같은 과제를 여러 번 반복하는 것은 과제 수를 늘리는 것과 같지 않습니다.

등급을 합치지 않습니다

쉬운 공개 과제 300개와 어려운 SoC 블록 20개를 합쳐 평균 내면 쉬운 과제가 점수를 결정합니다. 그래서 보고서는 등급별로 따로 보여 주고, 전체를 합친 순위는 만들지 않습니다.

7. 회사에 주는 가치

결정 사항벤치마크가 주는 근거
어떤 사내 모델을 운영할까같은 도구로 여러 온프레미스 모델을 비교해 RTL 과제에서 실제 성적이 좋은 모델을 고릅니다.
GPU 투자가 값어치를 하나더 큰 모델이 RTL 성공률을 얼마나 올리는지, 추가 시간은 얼마인지 측정합니다. 비용 환산은 측정된 값에만 적용합니다.
사내 모델과 상용 모델의 간격은사내 조합과 Claude 조합의 성공률 차이를 과제 영역별로 봅니다.
어떤 CLI를 표준으로 할까같은 모델을 쓸 수 있는 도구끼리 비교해 도구 자체의 효과를 분리합니다.
AI를 어떤 업무에 먼저 쓸까생성·수정·인터페이스 영역별 성적으로 잘하는 일부터 적용합니다.
업그레이드해도 괜찮을까모델이나 도구 버전이 바뀔 때 같은 시험을 다시 치러 성능 하락을 사전에 발견합니다.
사람 검토는 어디에 집중할까실패 원인 통계로 AI가 자주 틀리는 유형을 검토 항목에 넣습니다.

무엇보다 판단의 근거가 재현 가능한 기록으로 남습니다. 어떤 모델과 설정으로, 어떤 RTL을 제출해, 어떤 검사에서 왜 실패했는지 파일로 보존되므로 나중에 누구든 다시 확인할 수 있습니다. 사내 명세와 RTL은 외부로 나가지 않고 평가됩니다.

8. 할 수 없는 것

아직 실제 모델 성적은 없습니다. 지금까지 검증한 것은 채점기가 맞게 동작하는지입니다.

합격이 곧 양산 품질은 아닙니다. 정해진 시뮬레이션을 통과했다는 뜻이며, 전체 정확성의 증명이나 signoff가 아닙니다.

소수 과제 결과를 일반화하지 않습니다. 작은 블록을 잘 만든다고 SoC IP 전체를 설계할 수 있다는 뜻은 아닙니다.

주입 결함은 실제 버그가 아닙니다. 실제 버그 수정 능력은 사내 이력으로 만든 과제로 재야 합니다.

공식 점수와 비교하지 않습니다. 공개 과제는 변형했으므로 원본 벤치마크 점수와 다릅니다.

측정하지 않은 값을 채우지 않습니다. 비용이나 PPA를 측정하지 않았으면 0이 아니라 "미측정"입니다.

10. 자주 묻는 질문과 용어

AI가 정답을 미리 볼 수 있지 않나요?

평가 시 AI에게는 문제지만 전달하고, 정답과 숨은 검사는 다른 환경에 둡니다. 도구 자체가 이를 자동으로 막아 주지는 않으므로 운영 절차로 분리해야 합니다.

Claude Code로 사내 모델을 돌려서 도구를 고정할 수 없나요?

Anthropic은 Claude Code를 비 Claude 모델로 연결하는 구성을 지원하지 않는다고 안내합니다. 사내 모델끼리는 공통 실행 도구를 사용해 비교하고, Claude Code 구성은 별도로 비교합니다.

왜 공개 벤치마크 순위를 쓰지 않나요?

공개 순위는 참고가 되지만 사내의 명세 스타일, 인터페이스, 도구 제약을 반영하지 않고, 사내 모델과 설정은 애초에 포함되어 있지 않습니다.

시간이 얼마나 걸리나요?

채점 자체는 공개 과제 기준으로 짧습니다. 대부분의 시간은 AI가 답을 만드는 데 들어가며, 모델 속도와 과제·반복 수에 따라 달라집니다. 상용 시뮬레이터와 UVM을 쓰면 채점 시간과 라이선스가 주요 제약이 됩니다.

몇 번 반복해야 하나요?

같은 조건에서 3회 정도로 안정성을 보는 것을 권장합니다. 다만 비교의 신뢰도를 높이는 데는 반복보다 서로 다른 과제를 늘리는 것이 더 효과적입니다.

RTL
칩의 동작을 기술하는 코드 수준입니다. Verilog, SystemVerilog로 작성합니다.
testbench, checker
RTL에 입력을 주고 결과가 맞는지 확인하는 검사 코드입니다.
시뮬레이션
칩을 만들기 전에 RTL의 동작을 컴퓨터에서 실행해 보는 일입니다.
mutant
채점기를 시험하기 위해 일부러 결함을 넣은 RTL입니다.
seed
무작위 입력을 다르게 만드는 번호입니다.
온프레미스 LLM
회사 내부 서버에서 운영하는 언어 모델입니다.
harness, CLI agent
모델이 파일을 읽고 수정하며 도구를 실행하도록 돕는 프로그램입니다.
PPA
Power, Performance, Area. 전력·속도·면적입니다.
UVM
대규모 RTL 검증에 쓰는 표준 방법론입니다.
signoff
제조로 넘기기 전 최종 검증 승인입니다.
